# Irisync 実装計画

[Conductor検討書](conductor-feasibility-study.md)に沿って、先にWindows上の開発自動化環境を稼働させる。検証用Issueで設計承認から人間によるPRマージまで通した後、[基本設計書](basic-design.md)に沿ってIrisync本体を実装する。表の各行をGitHub Issueの起票単位とし、先行Issueと受入条件を引き継ぐ。

## 1. Conductor開発環境

検証用Issueを処理できるまでの基盤整備は手動で進める。Windows上のGo Polling ControllerがGitHub Projectsを監視し、ConductorのScriptステップが必要な工程でCodex CLIを呼ぶ。GitHub操作は `gh`、実行状態は専用SQLite、作業はIssueごとのGit worktreeを使う。

### 1.1 実装順序

| Issue | 先行 | 実装内容 | 受入条件 |
| --- | --- | --- | --- |
| C01 Windowsでの実行確認 | — | Conductor、Codex CLI、`gh`、Git、Goを実行ユーザーで起動し、動作した版を記録する。Scriptだけの最小YAMLを用意し、`conductor validate` と非対話実行で作業ディレクトリ、JSON結果、終了コードによる分岐、失敗・タイムアウト時の挙動を確認する。 | 日本語・空白を含むパスでも実行できる。成功と失敗を機械判定でき、ConductorのLLMプロバイダー認証なしで完走する。 |
| C02 GitHubとリポジトリ準備 | C01 | `gh` の認証とProjects権限を確認する。既存Projectと `Status` を調べ、必要に応じて作成・修正する。`AGENTS.md`、開発・レビュー・セキュリティ手順、Issue・PRテンプレート、基盤を検証するCIを用意する。承認者、自動化の実行アカウント、保護ブランチのマージ権限を設定する。 | 検証用IssueのStatusを読み書きできる。保護ルールを適用した検証用ブランチで、実行アカウントによる直接pushとPRマージが拒否され、人間は必要な承認とCI通過後にマージできる。 |
| C03 Polling Controllerと実行管理 | C02 | YAML設定、起動直後と既定5分間隔のポーリング、Projectsのページング、SQLiteによる実行ID・実行履歴・再試行の永続化、非同期プロセス監視を実装する。同時実行数の既定は1。Issue単位の排他、APIレート制限時のバックオフ、Ctrl+Cとタイムアウト時の子プロセス終了を扱う。 | ポーリングを継続しながらC01のワークフローを起動できる。同じIssueを重複起動せず、強制終了後はSQLite、GitHub、worktreeを照合して安全に再開できる。 |
| C04 Codex Adapterと設計承認 | C03 | `design.yaml` と `codex exec` の非対話アダプターを実装する。構造化結果、終了コード、変更ファイル、ログ、取得できる利用量を記録する。Issue別設計書を `docs/design/issues/issue-{number}.md` に保存し、承認者・設計コミットSHAを記録する。 | 未承認、承認者不一致、設計変更後の古い承認では実装を開始しない。`Design Review` 中はConductorプロセスが終了し、有効な承認をPolling Controllerが検知する。 |
| C05 実装とPR作成 | C04 | `implement.yaml` を実装する。承認済み設計を固定し、専用worktreeで実装する。ビルド・lint・静的解析・テストの後にAI自己チェックを行い、修正後は機械検証を再実行する。検証成功時にPRを作成する。 | 初回実装後の修正は最大3回。上限到達で `Blocked` に移る。PR作成後に処理が中断しても、再起動時は既存PRを照合して重複作成を防ぐ。 |
| C06 PRレビューとマージ確認 | C05 | `pr-review.yaml` と `merge-check.yaml` を実装する。コンフリクト確認、独立したCodexセッションでのレビュー、PRへの指摘投稿と同じPRでの修正、現行HEADに対するCI・レビュー結果確認を行う。人間からの修正指示は投稿者、投稿ID、対象コミットを確認して再開する。 | PRレビュー修正と人間の指摘対応は各最大3回で別々に計数する。コンフリクト解消は個別の回数・時間上限で止まる。新しいコミットは再検証し、マージをGitHub APIで確認した時点で `Done` へ移る。 |
| C07 運用確認と試験運用 | C06 | 検証用の小さな非アプリ変更を通じて全工程を運用する。認証エラー、再起動、Issueクローズ、PR差し替え、修正上限、ログと利用量を確認し、停止・復旧手順を記録する。 | 下記のアプリ着手条件を満たし、運用手順に沿って別の実行でも再現できる。 |

C01では、WindowsでConductor `0.1.47` のScript実行を検証した。C02では、管理用の `gh` 認証と `project` スコープを確認し、既存のProject #4に10種類のStatusを設定した。WindowsのCIと、Project・ブランチ保護を確認する手順は[開発手順](../development.md)を参照する。

C02では、実行用アカウントによるProject項目の更新と、`main` に適用されたマージ権限・必須チェック・承認条件を確認した。検証用PRを使った直接pushとマージ拒否の実地試験は省略し、C03へ進む。

### 1.2 実装前に決める運用仕様

- **C02とC04**で、Projectの所有者、番号、StatusのフィールドIDと選択肢ID、設計承認を記録する場所と承認者の識別方法を決める。承認対象に設計SHAを含め、大幅な設計変更は再承認する。
- **C03とC04**で、SQLiteのスキーマと一意制約、GitHub APIのバックオフ、Scriptステップの入出力とエラー分類を決める。GitHub操作の認証は実行管理側に置き、Codexの作業範囲を専用worktreeに制限する。Issue本文やレビューコメントは外部入力として扱う。
- **C05とC06**で、レビュー結果の構造、修正指示を取り込む条件、コンフリクト解消の試行上限を決める。ワークフローは保護ブランチ上の承認済み版を使い、実行するスクリプトとCIの権限を固定する。
- **C07**で、実行時間・Issue単位の予算上限、ログの保存先と機密情報の除去、利用量が取得できない場合の扱いを確定する。Windowsサービス化の要否は試験運用後に評価する。

### 1.3 アプリ着手条件

1. 検証用Issueが `Ready` から `Design Review` に進み、人間が設計を承認した後に実装・検証・PR作成・レビューが行われる。修正指示を受けた場合は同じPRで修正し、再検証する。
2. `Merge Ready` のPRを人間がマージし、Polling Controllerがマージを確認してIssueを `Done` にする。CI失敗やPRのHEAD更新時は、必要な再検証が終わるまで `Merge Ready` にしない。
3. 同じIssueの二重起動、承認前の実装、実行アカウントからの保護ブランチへの直接pushとマージを防げる。中断からの再起動、修正上限による `Blocked`、認証エラー時の起動停止を検証する。

## 2. Irisync本体

A01はC07の受入後に `Ready` にする。各Issueの詳細設計で対応する未決事項を確定し、人間の承認を経て実装する。Goの同期コントローラーとエージェントを先に接続し、最初の統合試験で1ペアの双方向同期を確認してから、複数ペア・運用機能・Web管理画面へ広げる。

### 2.1 実装順序

### 2.2 リリース受入

- **同期結果**。片側更新、初回同期、同一内容への両側更新、両側異内容、削除と更新の競合を検証する。優先側が反映され、失われる側のデータと衝突履歴が残ることを確認する。
- **データ保全**。サイズ超過、転送中の元・先の再更新、容量枯渇、置換前後の中断、Windowsの予約名・大小文字競合、シンボリックリンク／ジャンクションによるルート外参照を検証する。失敗時に危険な上書きや基準の先行更新が起きないことを確認する。
- **継続運用**。SSH切断・両側の全体走査・復帰、通常停止と即時停止、プロセス再起動、初回同期中断、大量イベント、複数ペアの障害分離、設定の再読込を通す。APIとUIの進捗・履歴・メトリクスが実際の処理と一致することを確認する。
- **配布**。Windows/Linuxのコントローラーとエージェントの組み合わせをOpenSSHで検証する。基本設計書の第17章の受入試験と第18章の確定要件No.1〜20をIssueと試験結果に対応付ける。 [基本設計書](basic-design.md)
