# Irisync 基本設計書

- **文書バージョン**: 1.0
- **作成日**: 2026-11-23
- **システム名**: Irisync（イリシンク）
- **位置付け**: 基本設計の最終版（機能要件 No.1〜20 を反映）。未確定の詳細設計事項は第19章に明記する。
- **対象OS**: Windows / Linux
- **実装言語**: Go（コントローラー・エージェント）、TypeScript（Web UI）

## 1. 目的・適用範囲

Irisyncは、SSH接続を使用し、ローカルサーバーA上の複数のフォルダと、それぞれのリモートサーバー上のフォルダを**1対1の同期ペア**として管理する双方向ファイル同期ツールである。サーバーAが同期判断を統括し、両側でファイル更新を検出する。衝突・削除時のデータ消失防止、同期履歴の保存、HTTP APIおよびWeb管理画面による可観測性・操作性を重視する。

### 1.1 基本原則

1. 各同期ペアは「A上のローカルルート1つ ↔ リモートルート1つ」の関係とする。同じAから複数のリモートサーバーへの接続を許可する。
2. A/B双方で更新を許容し、**前回正常同期時の基準状態**を使用して変更・衝突・削除を判定する。
3. SSHのみをリモート通信基盤とし、リモート側にHTTP待受ポートを要求しない。
4. ファイルは全体転送（ブロック差分転送なし）。転送は一時ファイル・ハッシュ検証を経由する。
5. 消失する可能性がある既存内容は退避する。衝突バックアップは自動削除しない。
6. 各ペアの制御、障害、進捗、優先順位、除外設定は独立させる。
7. CLI/同期エンジンはWeb UIなしでも動作する。Web UIは監視・操作を担当する。

### 1.2 対象外（初期版）

- rsync等のブロック単位差分転送
- シンボリックリンクの追跡・同期
- 所有者、ACL、パーミッション等の同期（更新日時は維持）
- 同一ディレクトリを共有する多対多同期
- SSH以外の独自ネットワーク転送プロトコル

## 2. システム構成

```text
               HTTP / Web UI (localhost:8080)
                          │
             ┌────────────▼─────────────┐
             │ Server A: Irisync        │
             │  Controller (Go)         │
             │  ├─ Pair manager         │
             │  ├─ Scheduler / Watcher   │
             │  ├─ Sync / Conflict      │
             │  ├─ SQLite               │
             │  └─ HTTP API + Vue SPA   │
             └───┬────────┬────────┬────┘
                 │        │        │ SSH stdio
          ┌──────▼──┐ ┌───▼─────┐ ┌▼────────┐
          │Server B │ │Server C │ │Server D │
          │Go Agent │ │Go Agent │ │Go Agent │
          │fsnotify │ │fsnotify │ │fsnotify │
          └─────────┘ └─────────┘ └─────────┘

 A:/folder1 <-> B:/shared  (pair-001)
 A:/folder2 <-> C:/shared  (pair-002)
 A:/folder3 <-> D:/shared  (pair-003)
```

### 2.1 A側コントローラー

- YAML設定ファイルの読み込み・検証・動的反映
- 同期ペア管理、起動/停止、スケジューリング、ローカルfsnotify監視
- OpenSSH起動・再接続・エージェント互換性確認
- 双方のメタデータ／SHA-256比較、転送指示、衝突処理、退避処理
- SQLiteによる最終同期基準・希望稼働状態・衝突・イベント・メトリクス管理
- REST API、SSE、Vue管理画面の配信

### 2.2 リモートエージェント

- SSHセッションから起動し、標準入出力でコントローラーと通信
- 指定されたリモートルート以下で再帰監視、走査、ハッシュ計算
- ファイルの読取、分割ストリーム転送、一時ファイルへの書込、検証、置換、退避
- ファイルイベントをAへ通知
- SSHの制御ストリームが閉じたときは安全に終了
- プロトコル通信はstdout、診断ログはstderrを使用

### 2.3 独立性とパスの重複禁止

ペアごとにキュー・状態・再接続・優先側を独立管理する。同一ローカルルートの重複、親子関係の重複、同一リモート実体への重複設定は原則拒否する。設定時に可能な範囲で検査し、解決できない実体パスの衝突は起動検査時にも検出する。

## 3. SSH接続・エージェント

### 3.1 OpenSSH利用

Goの `os/exec` からOpenSSHの `ssh` 実行ファイルを呼び出す。`~/.ssh/config` の `Host` エイリアスを利用可能とする。`HostName`、`User`、`Port`、`IdentityFile`、`IdentitiesOnly`、`Include`、`ProxyJump`、`ProxyCommand`、SSH Agent、known_hostsなどの動作はOpenSSHに委ねる。

```sshconfig
Host irisync-b
    HostName 192.168.1.100
    User syncuser
    Port 2222
    IdentityFile ~/.ssh/id_ed25519

Host irisync-c
    HostName 192.168.1.101
    User syncuser
    IdentityFile ~/.ssh/id_c
    ProxyJump gateway
```

起動例（概念例。実際のリモート実行パスと引数は詳細設計で固定）：

```sh
ssh -T irisync-b irisync agent --stdio
```

直接指定方式（ホスト、ポート、ユーザー、秘密鍵ファイルのパス）の設定もサポートする。秘密鍵自体やパスフレーズはIrisync設定ファイルに保存しない。接続のホスト鍵確認を無効化しない。

### 3.2 互換性確認

接続直後にエージェントとプロトコルバージョン・利用可能機能を交換し、非互換なら対象ペアの起動を中断してエラーを記録する。エージェントの配布・アップデート手順は詳細設計事項。

### 3.3 障害対応

SSH切断時は `connection_state=reconnecting` とし、実行中の転送を安全に失敗扱いにする。再接続後はエージェントを再起動し、**必ずA/B両方を全体走査**してから同期を再開する。接続障害は他ペアの動作を止めない。

## 4. 同期ペアとライフサイクル

### 4.1 起動方針

ペア単位で `startup: start | stop | restore` を指定する。

| 値 | 意味 |
|---|---|
| `start` | Irisync起動時に同期開始を要求 |
| `stop` | 起動時は停止 |
| `restore` | SQLiteに保存した前回の**希望稼働状態**を復元。履歴なしなら停止 |

希望稼働状態 `desired_state=running|stopped` と実際の実行状態を混同しない。異常切断は希望停止を意味しない。HTTP操作による希望状態の変更は先に永続化し、実処理を非同期で開始する。

### 4.2 状態モデル

| 軸 | フィールド | 値 |
|---|---|---|
| 希望状態 | `desired_state` | `running`, `stopped` |
| 実行状態 | `actual_state` | `stopped`, `starting`, `running`, `stopping`, `error` |
| 主要処理段階 | `phase` | `initial_scanning`, `initial_syncing`, `scanning`, `watching`, `waiting`, `syncing`, `none` |
| SSH接続 | `connection_state` | `disconnected`, `connecting`, `connected`, `reconnecting` |

`phase` は代表的な処理段階であり、監視・走査・転送が並行する場合の厳密な同時状態を一つの値で表さない。詳細な `active_transfers`、`pending_files`、`scan_progress` などを別に出す。

### 4.3 初期同期と復帰

- 最終同期基準がないペアは `initial_scanning` → `initial_syncing` → `watching` に遷移する。
- `initial_sync_completed` はSQLiteに保存する。
- 初期同期が中断された場合は未完了として再評価する。
- 初期同期済みのペアが停止・再接続から復帰する場合は `scanning` → 必要に応じて `syncing` → `watching` とする。
- 初期同期の完了条件は、初期走査完了、必要処理完了、同期基準の永続化、未処理の転送エラーなし。衝突が適切に解決・退避済みなら「人による確認待ち」の有無は完了判定を妨げない。
- 走査中は総数未確定の場合があり、進捗率を不正確に確定表示しない。

### 4.4 開始・停止

- 開始: SSH接続、エージェント起動、監視開始、全体走査、キュー反映、通常監視に移行。
- 通常停止: 新規転送を止め、実行中転送の完了を待って停止。
- 即時停止: 実行中の転送を中断。未完成の一時ファイルを安全に整理し、次回に再検証。
- Irisync全体はペアが全停止でもHTTP APIを提供し続ける。

## 5. ファイル監視と同期開始

### 5.1 監視

A/B両方でfsnotifyを使って作成・更新・削除・名前変更を検知する。サブディレクトリは再帰的に監視する。監視イベントを重複排除・集約する。自分の転送によるイベントも状態と照合して二重同期を防ぐが、自己イベントを無条件に捨てず外部変更を取りこぼさない。

### 5.2 ファイルごとの待機時間（確定）

- 最初の変更から **60秒以上** 経過し、最後の変更から **5秒以上** 無変更なら同期処理起動。
- そうでなくても最初の変更から **120秒** 経過したら同期処理を強制的に起動。
- 論理式: `(elapsed_first >= 60s && elapsed_last >= 5s) || elapsed_first >= 120s`。
- **120秒で強制するのは処理の起動**であり、不完全なファイルを無検証で上書きすることではない。
- 同期中・同期後の追加更新は新しい処理サイクルとして再判定する。

### 5.3 全体走査

監視イベントの欠落、SSH切断・復旧、停止中の変更、イベント過多を補正するため全体走査を行う。定期間隔は**暫定30分**。大量イベントはファイル単位に集約し、キューの量と同時転送数を制御する。

## 6. 同期判定

### 6.1 最終同期基準

ペアID＋相対パスを識別子とし、最後の成功時のファイル存在、種別、サイズ、SHA-256、更新日時、削除状態を保存する。必要なハッシュはAとBが各自ローカルに計算する。ハッシュ値だけが同じ場合も、実処理で必要な安全確認を行う。

### 6.2 通常の判定表

| Aの基準からの変化 | Bの基準からの変化 | 動作 |
|---|---|---|
| なし | なし | 何もしない |
| 内容更新 | なし | A→B |
| なし | 内容更新 | B→A |
| 同一内容への更新 | 同一内容への更新 | 内容一致を確認し、基準更新 |
| 異なる内容への更新 | 異なる内容への更新 | 衝突処理 |
| 削除 | なし | Bの既存内容を退避して削除を反映 |
| なし | 削除 | Aの既存内容を退避して削除を反映 |
| 削除 | 内容更新 | 衝突処理 |
| 内容更新 | 削除 | 衝突処理 |
| 削除 | 削除 | 削除状態を確定 |

ファイルとディレクトリの種別変更、大小文字衝突、競合リネーム等は自動上書きせず安全にエラー/衝突として扱う。詳細なリネーム最適化は未決定。

### 6.3 初回同期

| 初期状態 | 動作 |
|---|---|
| 片側のみ存在 | 存在する側からコピー |
| 双方に同一内容 | 同期済み基準を作成 |
| 双方に異なる内容 | 優先側を採用する衝突処理。失われる側を退避 |

初回同期で片側に存在しないことを「削除命令」と解釈しない。

## 7. ファイル転送と整合性

### 7.1 転送方法

ファイル全体をストリーム転送する。転送先と同じファイルシステム上の一時ファイルに書き、内容をSHA-256で検証してから反映する。更新日時を維持し、所有者・権限の同期はしない。

### 7.2 安全な処理順序

1. 元・先の現在状態と同期基準を取得。
2. 転送元のサイズ／SHA-256を確定し、転送対象が上限内か検査。
3. 既存内容を失わせる場合は退避を確保。
4. 一時ファイルにチャンク単位で転送。
5. 一時ファイルのハッシュと転送元の再確認を実施。
6. 反映直前に転送先が判定時から変更されていないことを確認。
7. 対象OS・ファイルシステムで安全な置換方法を選択し、正式名へ反映。
8. 実結果を再確認し、成功した同期基準だけSQLiteへコミット。
9. 途中で差異が出た場合は上書きせず、再試行または衝突判定に戻す。

> OS間で「条件付きの完全原子的置換」が常に保証されるわけではない。ルート/ファイル単位の協調的排他と変更再確認、クラッシュ復旧の詳細はD-09で確定する。

### 7.3 最大サイズ（確定）

- 全体デフォルト: **`1GiB` = 1,073,741,824バイト**。
- ペア単位で上書き可能。
- `max_file_size: 0` は無制限。
- 超過ファイルは `skipped_size_limit` として記録し、同期済みとは見なさない。
- 上限超過を理由に相手側ファイルを削除しない。
- 転送中に上限超過が判明したら中断し、一時ファイルを整理する。
- 上限以下になった場合や設定変更時は再評価する。

### 7.4 例外と除外

- ペアごとにglob除外を設定する。
- シンボリックリンクは追跡・コピーとも対象外。
- `.sync-conflicts` などのIrisync管理領域は必ず同期対象外。
- Windows/Linuxの禁止名、予約名、大小文字競合等は安全にエラー化する。

## 8. 削除と衝突

### 8.1 削除

削除操作も双方へ同期する。削除先にある内容を復旧可能な形で退避し、削除の事実（tombstone）を同期基準に記録する。削除と更新が競合すれば通常の衝突優先順位を適用する。

### 8.2 衝突

ペアごとに `conflict.priority: local | remote` を設定する。内容が一致しない両側更新、更新と削除の競合、初回両側異内容に適用する。優先側を採用し、失われる側の内容を退避してから反映する。同期失敗時に退避済みデータを失わないようにする。

### 8.3 バックアップと監査

- 衝突バックアップは**自動削除しない**。
- 退避領域 `.sync-conflicts` は同期対象から除外。
- 衝突ID、pair ID、パス、発生時刻、採用側、A/Bハッシュ、退避先、確認状態（未確認/確認済み）を記録。
- 衝突時の差分を後から再現できるよう、テキスト差分または当時の双方のスナップショットを保持する。保存方式・容量上限は詳細設計で確定。
- バイナリはハッシュ・サイズ・日時を提示。
- 復元操作は後から実装可能な構造とするが、APIの正式仕様は未確定。

## 9. Web管理画面（No.20：確定）

### 9.1 採用技術

| 層 | 技術 | 役割 |
|---|---|---|
| フロントエンド | **Vue 3** | SPA管理画面 |
| 言語 | **TypeScript** | UI・APIモデルの型安全性 |
| 開発・ビルド | **Vite** | 開発サーバーと静的アセット生成 |
| 状態管理 | Pinia（推奨） | ペア状態、通知などの共有状態 |
| 差分表示 | Monaco Diff Editor（推奨） | テキスト衝突の左右比較 |
| HTTPサーバー | Go `net/http` | API・SPA配信 |
| 配信方式 | Go `embed` | ビルド済みVueアセットをGoバイナリに内包 |
| ライブ更新 | SSE | 状態・進捗の一方向配信 |

**確定事項はVue 3 + TypeScript + Viteの採用**。PiniaおよびMonacoは実装推奨であり、依存ライブラリ選定は詳細設計で調整可能とする。SSR/Nuxtは導入せず、SPAとする。

### 9.2 配布・運用

- 開発時はVite開発サーバーを使用可能。
- リリース時はVueのビルド成果物をGoに `embed` し、**単一のGo実行ファイル**からHTTP APIと管理画面を配信する（リモートエージェントは対応OS向け別バイナリ）。
- 配布先にNode.jsランタイムを要求しない。
- フロントエンドは同期ロジックを保持せず、すべての制御・判定はGo APIに委ねる。

### 9.3 画面

1. **ダッシュボード**: 全体状態、接続数、同期待ち、衝突、エラー、転送量。
2. **同期ペア一覧・詳細**: ペア別の開始/停止、接続状態、起動方針、対象パス、設定。
3. **初期同期・通常同期進捗**: 走査済み数、総数（確定時）、転送ファイル・バイト、待ち・失敗数。
4. **衝突一覧・詳細**: 採用側、退避先、未確認/確認済み、テキスト差分。
5. **履歴・メトリクス**: 実行履歴、転送量、同期時間、エラー、再接続。
6. **設定画面**: 起動方針、除外、サイズ上限等。変更の検証と安全な反映。

Irisyncのロゴは、虹の女神イリスを抽象化したシンプルな単色・少色の図形を想定する。正式なロゴデータの指定は本設計の必須条件ではない。

## 10. HTTP API

### 10.1 基本方針

- A上のみで提供する。デフォルトで `127.0.0.1:8080` にバインド。
- 外部公開時はTLS/認証を必須とする。
- JSON REST APIで状態取得と開始/停止等を制御。状態イベントはSSE。
- 開始・停止要求は非同期処理とし、受け付けた時点で `202 Accepted` 等を返す。完了は状態APIとSSEで確認する。
- 失敗時は機密情報を含まないエラーコードと安全な説明を返す。

### 10.2 エンドポイント（基本案）

| メソッド | パス | 役割 |
|---|---|---|
| GET | `/api/v1/status` | 全体状態 |
| GET | `/api/v1/pairs` | ペア一覧 |
| GET | `/api/v1/pairs/{id}` | ペア状態・進捗 |
| POST | `/api/v1/pairs/{id}/start` | 開始 |
| POST | `/api/v1/pairs/{id}/stop` | 通常停止（即時停止指定は詳細設計） |
| POST | `/api/v1/pairs/{id}/sync` | 手動同期 |
| PUT | `/api/v1/pairs/{id}/startup` | 起動方針更新 |
| GET | `/api/v1/pairs/{id}/files` | 個別ファイル状態 |
| GET | `/api/v1/pairs/{id}/conflicts` | ペア別衝突 |
| GET | `/api/v1/conflicts` | 全体衝突一覧 |
| GET | `/api/v1/conflicts/{id}` | 衝突詳細 |
| GET | `/api/v1/conflicts/{id}/diff` | テキスト差分 |
| GET | `/api/v1/events` | イベント履歴 |
| GET | `/api/v1/metrics` | メトリクス |
| GET | `/api/v1/stream` | SSE |

### 10.3 状態応答例

```json

  "startup_mode": "restore",
  "desired_state": "running",
  "actual_state": "running",
  "phase": "initial_syncing",

  "initial_sync_completed": false,

    "scan": {"completed": true, "discovered_files": 1200},
```

### 10.4 SSEイベント

`pair_started`, `pair_stopped`, `phase_changed`, `file_changed`, `sync_started`, `sync_completed`, `conflict_detected`, `connection_lost`, `connection_restored`, `initial_sync_completed`, `sync_error` などを想定する。イベントの順序・再接続時の再送・イベントIDは詳細設計で確定。

### 10.5 差分表示

テキストの場合はUnified Diffの取得と左右比較ビューを提供する。バイナリまたは大きすぎる差分の場合は、メタ情報と表示不可の理由を返す。ファイル内容・差分は秘密を含み得るためアクセス制御する。

## 11. SQLite永続化

### 11.1 論理テーブル

| テーブル | 主な役割 |
|---|---|
| `pair_runtime_state` | 希望状態、初期同期完了、更新日時 |
| `sync_files` | `(pair_id, relative_path)` 単位の最終同期基準・tombstone |
| `sync_queue` | ペア別の同期待ち処理・再試行 |
| `sync_runs` | 実行開始/終了/結果 |
| `conflicts` | 衝突発生・解決・バックアップ・確認状態 |
| `events` | ファイル・SSH・状態変更イベント |
| `metrics` | 転送量、所要時間、エラー数等 |

### 11.2 希望状態

```sql
CREATE TABLE pair_runtime_state (
    pair_id TEXT PRIMARY KEY,
    desired_state TEXT NOT NULL CHECK (desired_state IN ('running', 'stopped')),
    initial_sync_completed INTEGER NOT NULL DEFAULT 0,
    initial_sync_completed_at TEXT,
    updated_at TEXT NOT NULL
);
```

実行中状態を再起動時にそのまま復元しない。状態はコントローラーの現実の処理状況から再構築する。

### 11.3 整合性

- 転送成功確認前に最終同期基準を進めない。
- 退避・反映・SQLiteコミットは中断可能性を考慮し、再起動時に検証・再実行できるよう冪等性を持たせる。
- 異常終了後に転送中だったファイルは実体とハッシュを再検査する。
- 削除のtombstoneを維持し、復活と誤判定しない。

## 12. 設定ファイル

形式はYAMLとする。**下記は設定例**であり、`full_scan_interval`、再試行間隔、同時実行数などは暫定値。Go/Vue実装で最終的な設定スキーマとバリデーションを整える。

```yaml
server:

    listen: "127.0.0.1:8080"

sync:

  idle_delay: 5s
  max_delay: 120s
  max_file_size: 1GiB
  full_scan_interval: 30m  # 暫定
  retry_interval: 5s       # 暫定

performance:
  max_concurrent_pairs: 5    # 暫定
  max_transfers_per_pair: 2  # 暫定

pairs:
  - id: pair-001
    startup: restore
    local:
      path: /data/folder1
    remote:
      ssh:
        host: irisync-b
        use_ssh_config: true
      path: /data/shared
    conflict:
      priority: local
    exclude:
      - "*.tmp"
      - ".git/**"

  - id: pair-002
    startup: start
    local:
      path: /data/folder2
    remote:
      ssh:
        host: irisync-c
        use_ssh_config: true
      path: /data/shared
    sync:
      max_file_size: 500MiB
    conflict:
      priority: remote

  - id: pair-003
```

### 12.1 動的変更

設定変更は再起動なしで反映可能とする。変更内容を検証してから切り替え、監視ルートやSSH接続先変更時は該当ペアを安全に再構築する。失敗した変更は適用せずエラーを記録する。稼働中の転送の扱い、設定ファイル再読込のトリガー、API経由更新と設定ファイルの優先順位は詳細設計事項。

## 13. OS・ファイルシステム互換性

- 内部識別子は相対パスで持ち、各OS固有のパスと分離する。
- Windowsの禁止文字・予約名・末尾ドット/空白、大文字小文字の衝突を検出する。
- 更新日時の解像度、タイムゾーン表記、ファイルシステムのrename/置換仕様を考慮する。
- ディレクトリ操作とファイル操作の順序関係を維持する。
- 同期ルート外に出るパス、シンボリックリンクやジャンクションを利用した逸脱を拒否する。
- 安全に表現できない場合は上書きせず、ファイル単位のエラーとしてWeb/APIに表示する。

## 14. 性能・大量更新

- 同一パスのイベントを集約し、待機タイマーの基準を管理する。
- ペア単位でキュー・転送並列数を制御し、全体同時接続数も制限する。
- 大容量ファイルはストリーミングし、ファイル全体をメモリに読み込まない。
- SSEで表示更新できる一方、表示頻度を適切に間引き、転送性能を妨げない。
- 大量イベントやfsnotifyエラー時には全体走査へフォールバックする。

## 15. メトリクス・監査

記録対象：成功/失敗ファイル数、送受信バイト数、同期所要時間、同期待ち数、衝突数、スキップ（サイズ超過・除外等）、SSH再接続数、最終成功同期日時、初期走査・転送進捗、エラー数。

イベントには `pair_id`、時刻、処理ID、パス（必要時）、種別、結果、エラーコードを含める。イベントの保存期間は未確定。衝突バックアップの「自動削除しない」と通常ログの保存期間は別の方針として扱う。

## 16. セキュリティ

1. SSHのknown_hosts検証を維持する。秘密鍵の内容を設定やログに保存しない。
2. HTTPの初期待受は `127.0.0.1:8080`。外部公開には認証とTLSを要する。
3. APIのパス引数・ファイル参照・差分閲覧はペアの同期ルートに制限する。
4. パストラバーサル、シンボリックリンク/ジャンクション経由の逸脱を防ぐ。
5. 同期設定、バックアップ、SQLiteを適切なOSアクセス権で保護する。
6. ログ・エラー本文に秘密鍵、認証情報、ファイルの機密内容を不用意に出さない。
7. 外部公開時は認証済み操作の監査ログ、CSRF等のWeb攻撃への対策を詳細設計に含める。

## 17. 障害復旧と受入試験の観点

| シナリオ | 期待結果 |
|---|---|
| A/Bの一方のみ編集 | 正しい向きに同期、同一ハッシュになる |
| 同時に異なる内容へ編集 | 優先側採用、失われる内容を退避、衝突履歴登録 |
| 更新と削除の競合 | 優先順位どおり処理、失われる内容を退避 |
| 初回片側のみ存在 | 存在する側からコピー |
| 初回双方異内容 | 自動無条件上書きをしない、衝突処理 |
| 60秒後かつ5秒無更新 | 同期処理起動 |
| 更新が続いて120秒経過 | 安全性を検証する同期処理を起動 |
| 1GiB超過 | 転送スキップ、同期済みとしない |
| 転送中に元・先が再更新 | ハッシュ・状態確認により危険な上書きを回避 |
| SSH切断・復旧 | ペアのみ再接続、双方全体走査、整合性を回復 |
| Irisync異常終了 | 希望状態を復元し、中断転送を再検証 |
| 初期同期中の停止 | 初期同期未完了を維持、再開時に安全に再評価 |
| Windows/Linux命名衝突 | 上書きしない、API/UIでエラー確認 |
| 大量の更新イベント | 集約・キュー制御、取りこぼしは全体走査で補完 |
| Web停止・再読込 | 同期エンジンは継続し、UIが最新状態に復帰 |
