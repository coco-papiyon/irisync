# Issue #31 設計書 — [A02-2] SQLite に同期状態を永続化する

## 目的・範囲

Irisync 本体の Go コントローラーに SQLite 永続化を追加する。マイグレーション、ペア別の最終同期基準と削除記録（tombstone）、同期待ち・再試行キュー、希望稼働状態、初期同期完了と進捗を扱う。再起動後にコミット済みの状態を読み戻し、`startup: restore` で希望状態の保存履歴がないペアは停止状態で開始する。同期結果に伴う SQLite の更新は一つのトランザクションで確定する。 [Issue #31](https://github.com/coco-papiyon/irisync/issues/31) · [基本設計 §4・§11・§19](https://github.com/coco-papiyon/irisync/blob/main/docs/design/basic-design.md)

- **対象外**　Conductor の Issue 実行状態用 SQLite と開発自動化基盤の変更。
- **後続 Issue**　A03 はファイル走査と OS 固有のパス検証、A04 は実ファイルの転送・退避・削除・反映と SQLite の間のクラッシュ整合性、A05 は監視イベントの集約・待機時間・キュー実行制御、A06 は開始・停止・SSH 再接続・運用復旧とイベント・メトリクス、A07 は HTTP API・SSE を扱う。#31 ではこれらが利用する永続化と起動時の状態判定を用意する。`sync_runs`、`conflicts`、`events`、`metrics` の機能実装は今回の必須範囲から外す。 [実装計画 §2.1](https://github.com/coco-papiyon/irisync/blob/main/docs/design/implementation-plan.md) · [基本設計 §11.1](https://github.com/coco-papiyon/irisync/blob/main/docs/design/basic-design.md)

## 実装計画

1. **Go コントローラーの DB 初期化層（R1）**。A01 の起動点と既存の依存関係を確認し、SQLite を開いて移行が完了してから永続化層を利用可能にする。提案として、版番号を DB 内に保持し、各移行とその版番号更新を同じトランザクションに入れる。対応する旧版が存在しない場合は、空 DB からの初回移行と現行版の再オープンを検証する。
2. **永続化層（R2～R5、R8～R9、R13）**。`sync_files` にペア ID と相対パスの複合キー、`pair_runtime_state` にペア ID の主キーと希望状態の制約を設ける。`sync_queue` はペア別に読み出せるようにする。提案として、希望状態を保存していないペアでも進捗を記録できる構造を選び、進捗の保存で希望状態の履歴が作られることを防ぐ。
3. **同期結果の書き込み境界（R10～R12）**。確認済み結果を受ける永続化処理に更新を集約し、同じ DB トランザクションをすべての更新で共有する。提案として、完了対象のキュー項目を識別して書き込むことで、処理中に追加された同じパスへの変更を誤って完了扱いにすることを防ぐ。同じ結果の再適用で進捗が二重計上されない条件を決める。
4. **コントローラーの起動時処理（R5～R9、R12）**。#30 の設定からペア ID と起動方針を取得し、保存済み状態を照合する。希望状態、現在の実行状態、以前の進捗を個別に扱い、中断項目を再検証対象として取り出せるようにする。

## 復旧手順

1. **移行失敗**。失敗した移行をロールバックし、コントローラーの同期開始を止める。DB を保持し、再オープンして版番号とデータを確認する。権限や容量などの原因を解消してから移行を再試行する。破損が確認された場合のバックアップ復元は運用判断とする。
2. **同期結果の更新失敗**。トランザクションを終了し、DB の基準・キュー・進捗を再読込する。ファイル反映済みの可能性がある場合は、後続の同期エンジンで実体とハッシュを照合してから再適用または再判定する。SQLite のロールバックでファイル側の変更は巻き戻らない。
3. **プロセス異常終了**。コミット済み状態から希望状態と進捗を復元し、初期同期の未完了と中断した作業を再評価する。ファイル側の再実行は実体確認後に行い、SSH 復旧時に必要な A/B 双方の全体走査は後続で実装する。 [基本設計 §3.3・§4.3・§7.2・§11.3](https://github.com/coco-papiyon/irisync/blob/main/docs/design/basic-design.md)

## D-07・D-08 の実装上の決定

- コントローラーは YAML の検証に成功してから、設定ファイルの隣に `設定ファイル名.state.sqlite3` を開く。`--state-db` で変更できる。明示した保存先の親ディレクトリは既存であること。同期対象のローカルルート内は保存先にできない。新規 DB ファイルは OS が対応する場合に所有者の読み書き権限で作る。Windows では親ディレクトリの ACL を継承する。
- ドライバーは Poller と同じ Pure Go の `modernc.org/sqlite` を使う。DB はローカルディスクを前提とし、WAL、`synchronous=FULL`、5 秒のビジー待機を設定する。DB の識別子と `user_version` を使い、初版の DDL と版番号を一つのトランザクションで確定する。
- `sync_files` のキーはペア ID と上位層で検証・正規化されたスラッシュ区切りの相対パス。文字列の大小文字・Unicode 表現は保持し、mtime は UTC の RFC3339Nano で保存する。削除確認済みの基準は tombstone として残す。
- キューには再利用しない ID を割り当てる。同一パスの新しい項目を別 ID にできる。確定結果の基準、該当キュー項目の削除、処理済み件数、該当する初期同期完了、結果の照合記録を同じトランザクションに入れる。再送された結果は同じ ID と内容の一致で冪等に処理する。コミット結果が不明な場合は新しい接続で照合記録を確認する。起動時に実行中だった項目は再検証待ちへ移す。実体とハッシュの確認は後続の同期エンジンが扱う。
- 希望状態と進捗は分離して保存する。進捗は走査・同期処理の件数と任意の総数を保存し、再起動では保持する。新しい全体走査の開始時に世代を切り替えてリセットする。旧世代の確定結果は基準とキューに反映しても、新世代の件数には加えない。
- `restore` の希望状態の履歴がなければ停止と判定する。読み出しエラーはコントローラー全体の起動エラーとする。起動時に同期や SSH 接続は開始済みと扱わない。同期エンジンと API の実装はそれぞれの後続 Issue が担う。
