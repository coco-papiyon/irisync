# [A01] Go CLI と Windows・Linux CI の設計・実装計画

## 目的と作業範囲

Irisync本体の `controller` と `agent` にGoの起動入口を設ける。`controller` は起動時にYAML設定を読み込めるようにし、両CLIをWeb UIなしで起動・終了できることをWindowsとLinuxのCIで検証する。

- `controller` は引数処理、設定読込、起動・終了処理を担当する。YAMLの読込とデコードをCLI本体から分け、A02で設定の意味検証を追加できる構造にする。
- `agent` は単独で起動・終了できる入口を持つ。将来の標準入出力による通信に備え、診断メッセージは標準エラー出力に送る。
- 後続Issueの範囲は、設定の意味検証・SQLite・ペア状態管理（A02）、SSH起動・通信・走査（A03）、同期処理（A04以降）、動的設定反映（A06）、HTTP API・Web UI（A07・A08）とする。

## 依存関係

- Issue本文の先行Issueは **#28**。実装計画では **C07の受入完了**がA01の着手条件となる。提示資料からは #28 とC07の対応や現在の完了状態を確認できないため、着手前に対応関係と `Blocked by` の登録を確認する。検証用Issueは、人間によるPRマージ後に同じProjectで `Done` に達していることを確認する。

- ビルドと検証にはGoツールチェーンおよびWindows・LinuxのCIランナーを使用する。Goのバージョン、コマンドの配置、設定ファイル指定の引数名は提示資料で未確定のため、既存のGo構成とCIを確認して実装時に決める。

## 実装手順

1. **CLIの入口を用意する。** `controller` と `agent` の引数処理、実行処理、終了コードの返却を組み立てる。各CLIに、初期化を通って正常終了するスモークテスト用の実行経路を設ける。
2. **設定読込を実装する。** `controller` が指定されたYAMLファイルを読み取り、起動に必要な最小限の構造へデコードする。ファイル未検出・読取失敗とYAMLの構文エラーを区別し、設定本文を出力せずに失敗理由を示す。同期ペアの検証や既定値の確定はA02に引き継ぐ。
3. **起動・終了をテストする。** 正常系では一時ディレクトリのテスト用YAMLを使い、ビルド済みの両CLIを実行する。異常系では存在しない設定ファイルと不正なYAMLを渡して終了コードと診断を確認する。スモークテストには実行時間の上限を設ける。
4. **両OSのCIに組み込む。** WindowsとLinuxで対象Goモジュールに同じ検証を適用する。`gofmt` による整形差分の確認、`go vet ./...`、`go test ./...`、両CLIのビルドとスモークテストを行い、PRでOS別の結果を確認できるようにする。

## 再実装で修正する YAML の読み込み

- A01 では設定を1つの YAML マッピングとしてパースし、YAML ノードの構造を保持する。重複キーを調べるために設定本文を Go の map や any に変換すると、配列などをキーに持つ有効な YAML まで失敗するため、YAML ノード上で同一マッピング内のキーを検査する。
- 文字列キーの重複はルートとネストしたマッピングの両方で拒否する。配列などの複合キーを Go の比較可能なキーに制限しない。重複と判断する場合は、キーのノード構造とタグ・値に基づいて比較する。設定項目の型やペアの妥当性は A02 で扱う。
- Windows・Linux の CLI テストに、ルートと入れ子の重複キーで失敗するケース、および入れ子の一意な配列キーを持つ有効な YAML で成功するケースを追加する。失敗時の診断には設定本文を含めない。
- CLI テスト内から Go のビルドを実行する場合は、Windows サンドボックスで Git メタデータの読み取りに依存しないよう -buildvcs=false を使う。GitHub Actions の Windows・Linux 両ジョブは実装 PR を作成してから結果を確認する。

## YAML キー比較の追加受入条件

- 先に、各マッピングのキーのエイリアスを解決し、解決先の YAML ノード自体をマッピング内で索引化する。同じ解決先を二つのキーが指している場合は、ノード内に再帰参照があっても重複として拒否する。この確認は内容に基づく指紋計算に先行させる。
- 循環のないキーはノードの種類・タグ・値と子の構造から得た指紋で候補を絞り、候補だけを比較する。完了した指紋と比較結果を再利用し、別のキーの全ペア比較や反復エイリアスの展開を避ける。内容が異なるキーを指紋の一致だけで重複扱いしない。
- 循環するキーの参照をたどるときは終了を保証する。循環を含むことを理由に同一ノードの重複検査を省略しない。別々の循環グラフに対する意味的な同値判定は A01 の範囲外とする。
- Windows・Linux の CLI テストで、一意な配列キーの成功、同一の文字列・配列キーとエイリアス経由の重複の拒否、コンパクトな入れ子エイリアスでの終了、多数の異なるキーでの成功を確認する。加えて同じ再帰ノードを参照するキーを持つ YAML を入力し、時間内に重複エラーを返し、設定値を診断に含めないことを確認する。再帰ケースの例を以下に示す。

```yaml
? &cycle [*cycle]
: first
? *cycle
: second
```

## 受入条件と検証方法

- [ ] 同じPRのコミットに対し、Windows・Linux両方のCIでGoテストと両CLIのビルドが成功する。
- [ ] 両OSでビルド済みの `controller` と `agent` がWeb UIやそのビルド成果物なしで初期化を完了し、制限時間内に終了コード `0` を返す。`controller` の正常系ではYAML設定読込を通ることをテストで確認する。
- [ ] 両OSで、読めない設定ファイルや不正なYAMLを指定すると `controller` が起動処理を打ち切り、非ゼロの終了コードと原因を判別できる診断を返す。診断に設定本文が含まれないことを確認する。

## 障害時の復旧

| 状況 | 対応 |
| --- | --- |
| 設定ファイルの読取・デコードに失敗 | 入力ファイルを保持したまま終了する。指定先、読取権限、YAMLの構文を診断に沿って修正し、起動し直す。 |
| CLIが制限時間内に終了しない | スモークテストが対象プロセスを終了させ、OSと対象CLIを特定できる結果を残す。終了処理を修正し、両OSで再検証する。 |
| 一方のOSでCIが失敗 | 失敗した工程を特定し、パスや実行ファイル名などのOS差を確認する。修正後のPRの最新コミットで両OSの検証が通ってから、人間によるマージに進む。 |
