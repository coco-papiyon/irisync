# Issue 34 初回同期と変更・削除の実装計画

## 目的と範囲

両側の観測結果と最後に確定した同期基準を相対パス単位で比較し、コピー、削除、衝突、基準更新、変更なし、再観測のいずれかを返す。走査の欠落と実際の削除を区別し、検証できなかったパスに対する破壊的な操作を防ぐ。 [Issue #34](https://github.com/coco-papiyon/irisync/issues/34) · [基本設計 §6–8・§11](../basic-design.md)

#31 の SQLite にある基準と tombstone、および #32 のルート制限付き走査の結果を入力に使う。転送、削除、退避、反映後の再確認、SQLite への書き込みは後続の実行処理の責務とする。 [#31 の設計](issue-31.md) · [#32 の設計](issue-32.md) · [実装計画 A04](../implementation-plan.md)

## 前提と着手条件

- Project #4 で #31 と #32 がともに `Done` であることを確認する。#31 の実装 PR はマージされ、Issue は完了としてクローズされている。 [Project #4](https://github.com/users/coco-papiyon/projects/4) · [PR #58](https://github.com/coco-papiyon/irisync/pull/58)
- 本計画のコミットを承認し、#34 専用の worktree で実装する。

## 入力と判定結果

- 同期基準は `state.Store.Baseline` の「履歴なし」「存在していたファイル」「削除確定済み」を区別する。読み出しエラーは判定を中止する。
- 片側の観測は「通常ファイル」「他の種別」「確認済みの不在」「未確認」のどれかを持つ。ファイルの内容は種別、サイズ、SHA-256 で比較する。更新時刻は実行時の再確認に使える観測値として保持する。
- 走査失敗、切断、未走査、変更、除外、名前エラー、衝突などの対象パスおよび配下は未確認とする。空パスの問題はルート全体に適用する。走査一覧にファイルが見つからない場合は、ルート境界内で対象の不在と種別を確認できたときだけ「確認済みの不在」とする。ディレクトリへの種別変更もここで識別する。 [#32 の部分走査の契約](issue-32.md)
- 判定結果には相対パス、操作の種類、コピー元または削除先、必要なら衝突理由と設定上の優先側を含める。優先側は後続の衝突処理に渡す。

## 判定規則

どちらかが未確認なら再観測に回す。通常ファイルと他の種別の衝突や安全に扱えないパスは自動反映の対象外とする。キーには #32 の検証済み相対パスを使い、表記を維持する。

| 基準と観測 | 判定 |
| --- | --- |
| 履歴なし。片側だけに通常ファイルがある | 存在する側からコピー |
| 履歴なし。両側が同じ内容 | 操作なしで基準を作成できると判定 |
| 履歴なし。両側の内容が異なる | 初回衝突 |
| 履歴なし。両側とも確認済みの不在 | 変更なし |
| 存在基準あり。両側の内容が基準と同じ | 更新時刻に差があっても変更なし |
| 存在基準あり。片側だけ内容が変わった | 変更側からコピー |
| 存在基準あり。両側が同じ内容に変わった | 操作なしで基準を更新できると判定 |
| 存在基準あり。両側が異なる内容に変わった | 更新の衝突 |
| 存在基準あり。片側が不在で他方は基準どおり | 基準どおりの側を削除する候補。反映前の退避が必要 |
| 存在基準あり。片側が不在で他方は内容が変わった | 削除と更新の衝突 |
| 存在基準あり。両側とも確認済みの不在 | 削除基準を確定する候補 |
| 削除基準あり。両側とも確認済みの不在 | 変更なし。tombstone を維持 |
| 削除基準あり。少なくとも片側に存在 | 再出現の衝突。実行側で処理が確定するまで tombstone を維持 |

削除基準からの再出現は、観測だけで意図的な再作成か判断できないため、衝突として扱う。実行側は判定後に観測が変わっていないことと、必要な退避が完了していることを再確認する。確認済みの結果だけを `state.Store.Apply` に渡し、基準を更新する。 [基本設計 §7.2・§8・§11.3](../basic-design.md)

## 実装順序

1. 内部の同期判定パッケージに観測、基準、判定結果の型と分類ルールを置く。判定関数は同じ入力に同じ結果を返し、I/O は呼び出し側が担当する。
2. #31 の基準と #32 の走査結果を判定入力へ変換する。観測したパスに加え、両側の一覧から消えた既存基準のパスを検査できるようにする。不在を裏付けられない候補は未確認として扱う。
3. 受入条件の事例を表テストで検証する。SQLite とルート制限付き走査を使う結合テストで、入力の意味が保たれることを確認する。
4. `gofmt`、`go vet ./...`、`go test ./...` を実行し、検証結果を PR に記録する。

## 受入条件と検証

| 試験 | 期待結果 |
| --- | --- |
| 初回で片側だけにファイル | 存在側からコピー。両方向を試す |
| 初回で両側の内容が異なる | 初回衝突。設定された優先側を結果に保持 |
| 基準と内容が同じで更新時刻だけが変化 | 変更なし |
| 両側の内容が変化 | 同じ内容なら基準更新。異なる場合は更新衝突 |
| 片側削除と他方変更 | 削除と更新の衝突。両方向を試す |
| 両側不在・片側削除 | 存在基準ありの場合のみ、それぞれ削除基準の候補と退避を伴う削除候補を返す |
| 部分走査、除外、ファイルからディレクトリへの変更 | 自動削除候補を返さない |
| 削除基準からファイルが再出現 | 衝突となり、削除基準は保持される |
