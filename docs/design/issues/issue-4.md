# [C07] Conductor試験運用の設計・実装計画

## 目的と変更範囲

人間による設計承認から、実装、PRレビュー、人間によるマージ、Polling Controllerによる `Done` 更新までを、文書1件の追加で検証する。C07の受入完了をIrisync本体のA01を `Ready` にする条件とする。

実装PRの差分は、新規ファイル `docs/conductor-pilot.md` の1件とする。UTF-8のMarkdownで保存し、末尾に改行を入れる。ファイルの内容は以下のとおり。

```markdown
# Conductor試験運用

設計承認から人間によるマージまでの動作を確認するための検証用ドキュメントです。
```

## 依存関係

- 直接の先行IssueはC06。C01〜C06で整備するWindows上のConductor、Codex CLI、Polling Controller、GitHub Projects、SQLiteによる実行状態管理、Issue専用Git worktree、Windows CIを利用する。
- 設計承認者とマージ権限を持つ担当者が必要となる。承認の有効性は、承認者と承認対象の設計コミットSHAで確認する。
- 試験開始前に、対象IssueのProject上の `Status` を読み書きできることと、保護ブランチに必要な承認・CI条件が設定されていることを確認する。

## 実装・検証手順

1. 対象Issueが `Ready` になったら、Polling Controllerが設計ワークフローを起動し、`Designing` を経て `Design Review` に進むことを確認する。人間の承認を待ち、承認済みの設計コミットSHAを記録する。
2. 有効な承認を検知したら `Implementing` に進み、Issue専用ブランチとGit worktreeで指定ファイルを追加する。差分が新規1件であること、見出しと本文が指定どおりであること、UTF-8で末尾に改行があることを確認してPRを作成する。
3. `PR Review` でコンフリクトを確認し、実装と独立したCodexセッションでレビューする。修正が必要な場合は同じPRに反映し、更新後のHEADに対して検証とレビューをやり直す。
4. 現行HEADのWindows CIが成功し、コンフリクトと未解決のレビュー指摘がなくなったら `Merge Ready` に進む。人間が最終確認してPRをマージする。
5. Polling ControllerがGitHub APIで対象PRのマージを確認した後、Project上の対象Issueを `Done` に更新したことを確認する。

## 受入条件

- 実装PRの差分が `docs/conductor-pilot.md` の新規追加1件で、指定の見出し・本文・文字コード・末尾改行を満たす。
- 承認前は実装が始まらず、有効な設計承認後に実装、PR作成、レビューが進む。修正が発生した場合は同じPRで再検証される。
- マージ対象のHEADでWindows CIが成功し、レビューが完了している。
- 人間がPRをマージし、Polling Controllerがマージを検知した後に対象Issueの `Status` が `Done` になる。
- 二重起動防止、保護ブランチへの自動化アカウントからの直接push・マージの防止、再起動からの復旧、認証エラー時の起動停止、修正上限による `Blocked` を運用確認し、再現できるよう結果を記録する。

## 停止・復旧

| 状況 | 対応 |
| --- | --- |
| GitHub APIの一時的な通信障害 | 次回ポーリングで再試行する。マージを確認できていない間は `Done` への更新を保留する。 |
| 認証・権限エラー | 新規ワークフローの起動を停止する。アクセス回復後にGitHubと保存済み状態を照合して再開する。 |
| Windows再起動、Controllerやワークフローの異常終了 | SQLite、GitHub上の承認・PR・コミット、worktreeを照合する。既存PRがあれば再利用し、未完了の工程から再開する。マージ済みで `Done` 更新だけが未完了なら、マージを再確認して更新する。 |
| CI失敗、PRのHEAD更新・差し替え、コンフリクト | `Merge Ready` への移行を保留し、対象PRと現行HEADを照合する。必要な修正、CI、再レビューを完了してから人間の最終確認に戻す。 |
| 修正上限 | 実装、PRレビュー、人間の指摘対応の修正回数を別々に管理し、それぞれ最大3回とする。コンフリクト解消には別の回数・時間上限を適用する。上限までに解決しなければ `Blocked` とし、人間の対応を待つ。 |
| Issueの中止・クローズ | 新規処理を停止し、既存PRとworktreeの状態を照合して後片付けする。 |

運用記録には停止・再開地点、再試行結果、ログの保存先、取得できた利用量を残す。利用量を取得できない場合は未取得として扱う。実行時間、Issue単位の予算上限、ログ保存先は試験運用で確定する。
