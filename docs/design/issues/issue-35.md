# Irisync Issue #35 [A04-2] 一時ファイルを使った安全な転送と置換

## 目的・範囲

A→BとB→Aのどちらでも、同期判定で選ばれた通常ファイルを受信側の同一ファイルシステム上に一時保存する。SHA-256、転送元の状態、反映直前の転送先の状態を検証してから正式名へ反映する。転送元の更新日時（mtime）を保持し、反映結果を確認してからSQLiteの最終同期基準を更新する。サイズ超過、切断、容量不足、再編集が発生しても、既存データと最後に確認済みの同期基準を保護する。 [Issue #35](https://github.com/coco-papiyon/irisync/issues/35) · [基本設計 §7・§11.3](https://github.com/coco-papiyon/irisync/blob/main/docs/design/basic-design.md)

本Issueでは転送と置換の経路、サイズ上限の適用、退避の確認、失敗時の状態引き渡しを扱う。ブロック差分転送、シンボリックリンクの追跡・同期、所有者・ACL・パーミッションの同期は対象外。削除反映、衝突の優先順位、退避領域の配置と容量方針はA04内の関連作業と接続する。監視・キュー制御はA05、SSH再接続後の両側全体走査と起動時の未完了転送の自動復旧はA06、実際のOpenSSHと配布物によるOS組み合わせの検証はA09で扱う。 [基本設計 §1.2・§8](https://github.com/coco-papiyon/irisync/blob/main/docs/design/basic-design.md) · [実装計画 §2](https://github.com/coco-papiyon/irisync/blob/main/docs/design/implementation-plan.md)

## 実装計画

変更箇所は責務単位で示す。具体的なパッケージ名とインターフェースは先行Issueの成果物を確認して確定する。

1. **設定・同期判定・SQLite読み出し（R1〜R7）**。コントローラーで全体設定とペア設定を解決し、確定したサイズで事前判定する。ストリーム受信側にも有効上限を渡し、実際の受信量を検査する。スキップ時は基準を保持し、後の再判定で現在値を使えるようにする。
2. **送受信・一時ファイル・退避（R8〜R11、R16、R18、R19）**。コントローラーとエージェントが、それぞれ受信側になるときに同じ反映手順を使う構成を提案する。同期ルート内の検証済みの配置先に、試行ごとに排他的に一時ファイルを作成する。書き込み・終了処理のエラーを確認し、一時ファイルを読み戻してSHA-256を照合した後に転送元を再確認する。
3. **ファイル反映とmtime（R12〜R14）**。同一ペア・相対パスへのIrisyncの反映を直列化し、検証済み一時ファイルへmtimeを設定した後、転送先を直前に再照合して置換する案とする。Linuxは同一ファイルシステム内の `rename` を候補とする。Windowsは既存先の置換と新規作成に適したOS操作を選び、共有モードやロックによる失敗を扱う。両OSで既存の正式ファイルを先に削除する方式を避ける。Linuxでも外部書き込みは協調排他の対象外であり、再照合から反映までの競合対策はD-09で決める。Windowsでは大小文字や予約名、ジャンクションの検証を含める。mtimeはタイムゾーン表記の文字列比較を避け、ファイルシステムで表現できる時刻として検証する。
4. **実結果確認と基準確定（R15、R17）**。正式名の存在・種別、サイズ、SHA-256、mtimeを確認してから、コントローラーがSQLiteに基準をコミットする。反映結果が不明な試行を識別し、同じファイルを再実行しても退避や同期基準を損なわない構成をD-09で確定する。 [基本設計 §7・§11.3・§13・§19](https://github.com/coco-papiyon/irisync/blob/main/docs/design/basic-design.md)

## 復旧手順

1. **反映前の失敗**。ストリームとファイルを閉じ、当該試行の一時ファイルだけを整理する。残存時は試行と結び付けて追跡する。容量を回復した場合も、前回の判定を使い回さず元・先を再確認してから再試行する。退避済みデータは保持する。
2. **反映の有無が不明、または反映済みでSQLite更新に失敗**。正式名の実体とSHA-256、元の現在状態、旧基準、利用可能な退避を突き合わせる。確定予定の結果と安全に一致すると確認できた場合は基準更新を再実行する。旧状態が確認できれば通常の再判定に戻す。説明できない差異は衝突またはファイル単位のエラーとして扱い、正式ファイルと退避を保持する。この分岐はD-09の復旧案とする。
3. **SSH切断後の復帰**。A06の再接続処理でA/B双方の全体走査を行い、中断ファイルを再評価してから同期を再開する。 [基本設計 §3.3・§8・§11.3](https://github.com/coco-papiyon/irisync/blob/main/docs/design/basic-design.md) · [実装計画 §2.1](https://github.com/coco-papiyon/irisync/blob/main/docs/design/implementation-plan.md)

## 未確定事項

- **D-09の競合検出と置換保証**。元・先の期待状態の項目と照合方法を確定する。mtimeとサイズが同じ内容変更を検出するため、内容ハッシュも照合に使う案。Irisync内の排他の単位と範囲、外部プロセスが最終照合後に変更した場合の保証範囲、保証を満たせないファイルシステムで反映を拒否する条件を決める。
- **D-09のクラッシュ整合性**。一時ファイルと退避の識別情報、反映前後に永続化する状態、ファイルやディレクトリの永続化を確認する順序、SQLiteコミット失敗時の再照合条件を確定する。#35で作る復旧用の状態とA06の自動復旧の責務も確認する。
- **D-18のOS別仕様**。LinuxとWindowsで既存先あり・なしに使う置換操作、サポートするファイルシステム、Windowsの共有違反時に再試行する条件、mtimeを設定・取得する順序と解像度ごとの比較規則を決める。Issue #35はD-18を指定し、実装計画はA03にパス処理、A09に実機確認を割り当てている。本設計では#35を置換・mtimeの仕様決定と実装時検証の担当とする案を示した。
- **先行Issueとの契約**。#33・#34が提供する転送RPC・キャンセル、状態照合、基準更新のインターフェースを確認する。D-10で定める退避領域が容量不足の場合の運用、D-12に関係する転送中の設定変更の適用時点も確認する。設定変更は次の試行から適用する案。
- **CIでの実機能の確認範囲**。Windows/Linuxランナーで共有違反や容量不足を制御できる範囲と、A09で確認するファイルシステム・OpenSSHの組み合わせを決める。 [Issue #35](https://github.com/coco-papiyon/irisync/issues/35) · [基本設計 §19](https://github.com/coco-papiyon/irisync/blob/main/docs/design/basic-design.md) · [実装計画 §2](https://github.com/coco-papiyon/irisync/blob/main/docs/design/implementation-plan.md)
